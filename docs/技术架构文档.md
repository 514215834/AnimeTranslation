## 1. 项目概述

### 1.1 项目定位

面向**字幕组与个人译者**的"生肉 → 精翻熟肉"AI 辅助翻译平台，以**日语 → 中文**为主要语向，架构上支持任意语向组合。核心定位是 **AI 辅助提效 + 人工质量把关（human-in-the-loop）**：语音识别（ASR）、OCR、LLM 完成初稿生产，译者在 Web 复核工作台完成校对终审。

### 1.2 目标用户

| 用户 | 使用方式 |
|---|---|
| 个人译者 | 单机 Docker 部署，一人完成整季番剧字幕翻译 |
| 字幕组小团队 | 组内多角色协作（翻译 / 校对 / 终审），流程化生产 |
| 进阶用户 | 通过开放 API / CLI 批量处理（M4 提供） |

### 1.3 设计原则

1. **AI 提效、人把质量关**：AI 产出高质量初稿，终审权在人。
2. **Provider 可插拔**：ASR / OCR / LLM 全部抽象为统一接口，随时更换引擎或渠道。
3. **Stage 产物落盘、断点续跑**：重跑只跑失败部分，token 与算力成本可控。
4. **单机优先、平滑扩展**：SQLite 起步，可平滑升级 PostgreSQL + 分布式 worker。
5. **合规红线**：仅处理用户自有授权素材，不内置任何片源站点抓取能力。

### 1.4 术语约定

| 术语 | 说明 |
|---|---|
| 生肉 / 熟肉 | 无字幕原片 / 带翻译字幕的成品 |
| Segment | 字幕行（一条台词），含时间轴、原文、译文与状态 |
| Stage | 流水线阶段（媒体接入、ASR、翻译、质检等） |
| Provider | 可插拔的 AI 能力实现（如某一家 LLM 渠道、某一个 ASR 引擎） |
| CPS | 每秒字符数（Chars Per Second），字幕可读性核心指标 |

## 2. 总体架构

### 2.1 架构总览

```
┌────────────────────────────────────────────────────────────────┐
│                           接入层                                │
│     Web UI (Vue3 + artplayer + wavesurfer)  │  REST API  │ CLI (M4) │
├────────────────────────────────────────────────────────────────┤
│                     应用服务层（FastAPI）                        │
│   番剧项目管理 │ 剧集管理 │ 任务调度 │ 术语库 │ 审核流 │ 用户权限   │
├────────────────────────────────────────────────────────────────┤
│                      流水线引擎（Pipeline）                      │
│     Stage 状态机 │ 断点续跑 │ 产物缓存 │ 失败重试 / 降级           │
├────────────────────────────────────────────────────────────────┤
│                    AI Provider 层（可插拔）                      │
│   ASR: faster-whisper │ 对齐: WhisperX │ OCR: PaddleOCR          │
│   LLM: OpenAI 兼容统一网关（GPT/Claude/Gemini/DeepSeek/Qwen/     │
│        Ollama/SakuraLLM 全兼容）                                │
│   [扩展点] TTS / 人声分离 —— AI 配音暂不规划，仅保留接口           │
├────────────────────────────────────────────────────────────────┤
│                         媒体处理层                               │
│        FFmpeg：探测 / 抽音轨 / 转码 / 字幕封装 / 硬压             │
├────────────────────────────────────────────────────────────────┤
│                       数据与存储层                                │
│   SQLite → PostgreSQL │ 文件存储 本地卷 → MinIO │ Redis（v1.0）   │
└────────────────────────────────────────────────────────────────┘
```

## 3. 核心流水线设计

### 3.1 Stage 定义

| # | Stage | 产物 | 说明 |
|---|---|---|---|
| S1 | ingest 媒体接入 | `audio.wav`(16k mono) + `media.json` | FFmpeg 抽取音轨、探测时长/分辨率/音轨 |
| S2 | asr 语音识别 | `transcript.json` | faster-whisper 逐行时间轴 + 原文；语言与模型可配 |
| S3 | ocr 硬字幕识别（可选） | `ocr_track.json` | 场景抽帧 → PaddleOCR → 跨帧聚类去重，产出"屏幕文字轨" |
| S4 | translate 初翻 | segments(译文初稿) | LLM 批量翻译：上下文窗口 + 术语注入 + 结构化输出 |
| S5 | polish 润色（可选） | segments(润色稿) | 第二轮 LLM 以校对身份润色；可换更强的模型 |
| S6 | subtitle 字幕工程 | `output.srt` / `output.ass` | 时间轴校正 + 样式模板 + 双语布局 |
| S7 | qa 质检 | `qc_report.json` | 规则检查，产出告警清单（不阻断流程） |
| S8 | review 人工复核 | segments(终稿) | **人工环节**：Web 复核工作台逐行校对 |
| S9 | export 交付 | 成品文件 | SRT / ASS / MKV 软字幕封装 / MP4 硬压 |

S3 的"屏幕文字轨"（signs）与 S2 的"对白轨"（dialogue）按类型区分，导出时映射到 ASS 的不同样式。

### 3.2 状态机

```
pipeline_job: queued → running → succeeded | failed | canceled
                                  │（支持暂停后恢复）

stage_run:    pending → running → succeeded | failed | skipped
```

失败策略：
- 单 Stage 失败只重试该 Stage，不重跑整条流水线；
- translate 阶段为**行级**失败处理：仅补翻缺失/校验失败的行；
- Stage 连续失败 N 次（默认 3）后整 Job 置为 failed，保留已完成产物。

### 3.3 断点续跑与产物缓存

- 每个 Stage 产物落盘至 `data/artifacts/{job_id}/{stage}.json`；Job 重跑时已成功 Stage 直接复用（例：只重跑翻译不重跑 ASR，节省大量时间与 token）。
- translate 阶段内部再做 **segment 级译文缓存**：key = `hash(原文) + 模型 + prompt版本 + 术语表版本`，命中直接复用，不重复调用 LLM。

## 4. 关键模块设计

### 4.1 AI Provider 层（可插拔接口）

```python
class ASRProvider(Protocol):
    def transcribe(self, audio_path: str, language: str) -> TranscriptResult:
        """返回逐行 [{start_ms, end_ms, text, confidence}]"""

class OCRProvider(Protocol):
    def recognize(self, frame_paths: list[str]) -> list[OcrLine]:
        """返回帧内文字块及坐标"""

class LLMProvider(Protocol):
    def chat(self, messages: list[dict], json_mode: bool = True,
             max_retries: int = 3) -> LLMResponse:
        """统一 OpenAI Chat Completions 兼容协议"""
```

- **LLMProvider 统一走 OpenAI 兼容协议**：一套代码接入 GPT / Claude / Gemini / DeepSeek / Qwen / Ollama / SakuraLLM（本地）。
- 渠道配置项：`base_url / api_key / model / 并发数 / 速率限制 / 费率`；API Key 使用 Fernet 加密落库。
- 注册机制：内置 Provider + 插件目录扫描（M4 开放规范）。
- **扩展点（暂不开发）**：`TTSProvider`、`VocalSeparationProvider` 接口已预留签名，启用 AI 配音时不改动主架构。

### 4.2 LLM 翻译引擎（质量核心）

| 策略 | 设计 |
|---|---|
| 批次 | 每批 15 行左右，携带**前 3 句已译结果 + 后 3 句原文**作为窗口上下文 |
| Prompt | system 定义角色为"资深动漫字幕翻译"，明确口语化、语气词、称谓处理规范 |
| 术语注入 | 命中术语表/角色表的词条注入当批 prompt，锁定译法 |
| 前情摘要 | 剧集级 summary（可人工填写、可由 LLM 依前集生成），注入以保持跨集一致性 |
| 结构化输出 | 要求 JSON 数组 `[{"i": 行号, "zh": 译文}]`；行号校验，缺行/错行单独补齐重试 |
| 双轮 | S4 初翻（可用便宜模型）→ S5 润色（可用强模型），均可在项目级配置开关 |
| 重试与降级 | 指数退避重试；降级链：主渠道 → 备用渠道 → 标记该行"待人工"，不阻塞整集 |
| 成本控制 | 译文缓存（见 3.3）+ Stage 级断点重跑 + 每 Job 记录 token 用量与费用估算 |

### 4.3 字幕引擎

- 基于 pysubs2 读写 SRT / ASS / VTT。
- **时间轴校正规则**（S6）：消除重叠、最小间隙 ≥ 100ms、单行最短显示 ≥ 1s、最大单行时长 ≤ 6s（超出则智能拆行）。
- **ASS 样式模板**：默认"底部对白 + 顶部注释"两种样式；字体/字号/描边/阴影/边距可配置；支持项目级自定义模板；双语布局默认日上中下。
- 硬压（S9）统一由 FFmpeg 完成：软字幕封装 MKV（`subtitles` 轨挂载）或 ASS 硬压 MP4（`libass` 滤镜）。

### 4.4 质检引擎（S7 规则清单）

| 类别 | 规则 |
|---|---|
| 时间轴 | 重叠、间隙过小、CPS 超限（中文默认 > 15 告警）、最短/最长显示时长 |
| 内容 | 空译文、译文字数/原文字数比例异常、疑似漏译（原文非空译文为空） |
| 一致性 | 同一原文在不同集的译法与术语表不一致、角色称谓前后不一致 |
| 格式 | 非法字符、引号规范、单行建议字数（ASS 中文每行 ≤ 16 字，超出提示手动断行） |

### 4.5 硬字幕 OCR 流程（S3）

1. PySceneDetect 场景切换检测 + 固定间隔（默认 0.5s）抽帧；
2. 帧内字幕区域检测（底部/顶部条带优先）→ PaddleOCR 识别；
3. 跨帧文本聚类去重（相近时间 + 文本相似 → 合并为一行，取起止帧为时间轴）；
4. 产出 signs 轨，标记为"屏幕文字"类型，供翻译与导出。

### 4.6 人工复核工作台（前端）

三栏布局：

```
┌──────────────────────────────────────────────────────┐
│ 视频预览 (artplayer)  + 波形图 (wavesurfer)            │
├──────────────────────────────┬───────────────────────┤
│ 字幕表格                      │ 上下文面板              │
│ # | 时间轴 | 原文 | 译文 | 状态 │ · 术语表命中高亮       │
│ （行点击 → 视频跳转；          │ · 角色表               │
│  行内编辑；时间轴微调）        │ · QC 告警定位          │
└──────────────────────────────┴───────────────────────┘
```

快捷键：空格播放/暂停、↑↓ 上下行、Enter 下一行、L 锁定行。行级状态（见 5.1）与审核流联动。

### 4.7 Bangumi 元数据集成

搜索匹配番剧 → 拉取名称 / 话数 / 简介 / 角色与 CV → **自动创建角色表与术语建议**（人名、地名、招式名）→ 人工确认后生效。减少人名错译，是日语番剧质量的关键抓手。

## 5. 数据模型

### 5.1 ER 关系

```
Project(番剧) 1 ── n Episode(集) 1 ── n PipelineJob 1 ── n StageRun
                                └── n Segment(字幕行)
Project 1 ── n GlossaryTerm / Character
User n ── n Role ；ReviewRecord(审核记录) 挂在 Segment 上
TranslationMemory(翻译记忆，M3)
VoiceProfile(音色表——仅建表预留，暂不实现业务)
```

### 5.2 核心表结构

**project（番剧项目）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id / title | — | 主键 / 番剧名 |
| bangumi_subject_id | int? | Bangumi 条目 id |
| source_lang / target_lang | str | 默认 `ja` / `zh-Hans` |
| pipeline_config | JSON | 项目级默认流水线配置（模型、双轮开关等） |
| status | enum | active / archived |

**episode（集）**：`id, project_id, number, title, video_path, duration_ms, status`

**pipeline_job（流水线任务）**：`id, episode_id, state, current_stage, config(JSON), error, token_cost, created_at/finished_at`

**stage_run**：`id, job_id, stage, state, artifact_path, error, retry_count, started_at/finished_at`

**segment（字幕行，核心）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id / episode_id / index | — | 行号 |
| start_ms / end_ms | int | 时间轴 |
| source_text / target_text | text | 原文 / 译文 |
| track_type | enum | dialogue / signs（对白 / 屏幕文字） |
| speaker | str? | 说话人（ASR 分离或人工指定） |
| status | enum | draft → translated → reviewed → final |
| locked | bool | 锁定后 AI 重跑不覆盖人工修改 |
| qc_flags | JSON | 命中的质检规则列表 |

**glossary_term**：`id, project_id?, source, target, aliases, note, locked`（`project_id` 为空表示全局术语）
**character**：`id, project_id, name_jp, name_cn, aliases, cv, description`
**translation_memory**（M3）：`source_hash, source, target, model, quality, used_count`
**user / role / review_record**：账号、角色（admin/translator/reviewer）、行级审核记录

## 6. API 设计（REST 概要）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/projects` | 创建番剧项目 |

```
docker-compose.yml
 ├─ api        FastAPI + 内置 asyncio worker（含模型推理）
 ├─ web        Nginx：前端静态资源 + 反代 /api
 └─ volume ./data   ├── app.db (SQLite)
                    ├── media/    上传视频
                    ├── artifacts/ 各 Stage 产物
                    └── models/   whisper 等本地模型
```

### 7.2 v1.0（团队版拓扑）

```
web(nginx) ── api(FastAPI ×N) ── Redis ── Celery worker(CPU)
                                │        Celery worker(GPU, 任务标签路由)
                                ├── PostgreSQL
                                └── MinIO（媒体与产物）
```

GPU worker 通过 Celery 任务标签（`gpu`）路由，CPU 任务（翻译、QA）与 GPU 任务（ASR）分离伸缩。

### 7.3 GPU 与模型资源

| 模型 | 显存（int8/fp16） | 说明 |
|---|---|---|
| faster-whisper large-v3 | ~5 GB | 首选；CPU 可退 small/medium（速度换显存） |
| Sakura-13B（GGUF Q4，可选本地） | ~9 GB | 本地兜底翻译渠道，vLLM/llama.cpp 提供 OpenAI 兼容接口 |
| PaddleOCR | ~1 GB | 可与 ASR 共卡调度 |

模型在容器首启时下载至 `models/` 卷，支持离线包导入。

## 8. 非功能设计

| 维度 | 设计 |
|---|---|
| 性能基线 | 24 分钟单集：GPU 下 ASR 约 2~5 分钟；LLM 约 300~500 行 × 双轮，集内并发默认 4，整季按集并行 |
| 成本 | 每 Job 记录 token 用量与费用估算（按渠道费率配置），项目级成本看板（M3） |
| 可观测性 | loguru 结构化日志；stage_run 表即任务审计；Prometheus 指标预留 |
| 安全 | JWT 鉴权（M3）；API Key Fernet 加密落库；上传文件类型与大小白名单 |
| 合规 | 仅处理用户自有授权素材；不内置片源站点抓取；本地部署数据不出域 |
| 可用性 | Worker 崩溃后 Job 可从最后成功 Stage 恢复；产物与 DB 事务一致 |

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| LLM 成本与速率限制 | 分批并发 + 译文缓存 + Stage 断点重跑；本地 SakuraLLM 渠道兜底 |
| 人名/术语错译 | Bangumi 自动预填角色表 + 术语锁定 + QA 一致性检查 |
| 时间轴漂移 | WhisperX 词级对齐 + S6 规则校正器 + 人工波形对轴 |
| 长番跨集一致性 | 前情摘要（人工填写 + LLM 生成两级）+ 全局术语表版本化 |
| OCR 对动画特效字识别率低 | 仅作为 signs 辅助轨并标注置信度，人工确认后采纳 |
| pysubs2 对复杂 ASS 特效支持有限 | 特效定位为"模板化样式"，卡拉OK/复杂特效列入 Backlog |
| 版权合规 | 默认本地部署；不内置片源抓取；文档明示仅处理自有授权素材 |
